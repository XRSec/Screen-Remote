# Edit Session Dialog Layout Notes

## 背景

这次问题出现在“编辑会话”对话框重构之后。表面上看是若干零散的 UI 小问题，但本质上是几类不同布局被抽成通用组件后，约束模型没有完全区分清楚。

受影响的主要是两类行：

- 输入行：例如 `会话名称`、`主机`、`端口`
- 选项行：例如 `选择分组`、`关键帧间隔`、`视频编码器`、`音频解码器`、`强制使用 ADB 转发`

## 现象

- 左侧标题和帮助提示图标之间有时会被拉开很远
- 输入框没有真正吃掉剩余空间，看起来不像“右侧大输入区”
- 右对齐输入时，光标会压在最后一个字符附近
- 右侧选项值虽然位置正确，但会过度贴近右边缘
- 开关行本来放得下完整标题，却被过早截断

## 根因

### 1. 不同类型的行，被套用了相同的宽度策略

输入行、开关行、下拉行、可点击行虽然长得类似，但右侧控件的占位模型并不一样：

- 输入行的右侧应该尽量吃满剩余空间
- 开关行的右侧只需要给开关留固定宽度
- 选择器/编码器这类行的右侧需要固定的“值显示区 + 图标区”

如果把它们都用同一套“固定最大宽度”或“统一收缩策略”处理，就会出现：

- 有些行明明还能显示完整文字，却被提前省略
- 有些行的右侧内容又会显得贴边或者拥挤

### 2. 标题文字和帮助提示图标没有被当成一个内容组处理

最初的问题之一是：

- 标题文字本身被拉伸
- 帮助提示图标独立放在标签容器尾部

这样一来，图标跟的是“容器边界”，不是“标题文字结尾”，于是视觉上就会出现“图标离文字很远”。

正确的思路应该是：

- 标题文字和提示图标属于同一个内容组
- 文本优先占用可用宽度
- 图标紧跟文本，而不是紧跟整个标签区域的边界

### 3. 右对齐输入只处理了“贴右”，没有处理“光标缓冲”

单纯把输入文本设为右对齐，只能解决“内容向右收拢”的问题，但不能解决“光标压住最后一个字符”的问题。

原因是：

- 文本最后一个字符和插入光标共享尾部位置
- 在右对齐、窄行高、较紧凑字体下，这个问题会更明显

所以这里只靠外层 padding 不够，还需要给显示层额外留一个很小的尾部可视空位，让光标落在字符后面一点，而不是压在最后一个字上。

### 4. 固定宽度右侧区域缺少内部缓冲

像 `关键帧间隔`、`音频解码器` 这类右侧值显示区，本身是固定宽度设计，这没有问题。问题在于：

- 固定宽度只是保证不和左侧标题抢空间
- 但如果内部没有额外右边距，文本会显得过于贴右

也就是说，“固定宽度”解决的是整体排版问题，“内部 padding”解决的是观感问题，两者不能互相替代。

## 修复思路

### 输入行

输入行采用以下策略：

- 左侧标题区宽度受控，但标题和提示图标作为一个整体排版
- 右侧输入区直接吃掉剩余空间
- 输入内容保持右对齐
- 输入区额外保留尾部可视空间，避免光标压住最后一个字符
- 输入区本身也保留适度右边距，避免内容过于贴边

### 开关行

开关行采用以下策略：

- 右侧只为开关本身保留固定宽度
- 左侧标题区使用剩余空间
- 提示图标紧跟标题文字
- 不再对标题文本施加不必要的硬上限

这保证了“放得下就完整显示，放不下才省略”。

### 选择器/编码器/解码器行

这类行采用以下策略：

- 右侧继续使用固定宽度内容区，避免和左侧标题互相抢位
- 固定宽度内容区内部增加左右 padding
- 值文本在该区域内部右对齐
- 箭头或提示符号与文本作为同一组内容处理

这样既能保证整体对齐，也不会让右侧内容显得过分贴边。

## 这次真正需要区分的布局规则

后续如果继续改这块 UI，建议始终先判断一行属于哪一类，再决定约束方式：

- 输入行：右侧是可伸缩编辑区
- 开关行：右侧是固定宽度开关
- 选项行：右侧是固定宽度展示区

不要把这三类行用同一个“统一最大宽度”规则强行压平，否则很容易再次出现：

- 标题和提示图标分离
- 可显示完整的文字被错误截断
- 右侧值过于贴边
- 输入光标压住末尾字符

## 结论

这次问题不是单个控件样式错误，而是“通用组件抽象后，没有把不同交互类型的布局约束区分开”。

真正稳定的做法不是继续加零散的 margin，而是明确：

- 哪些行的右侧应该吃满
- 哪些行的右侧应该固定宽度
- 哪些元素必须被视为一个内容组

只要这三个原则守住，编辑会话页这类 iOS 风格的紧凑表单就会稳定很多。
